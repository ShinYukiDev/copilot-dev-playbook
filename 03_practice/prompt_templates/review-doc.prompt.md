以下の文書を、バランス型（厳しすぎず甘すぎない）でレビューしてください。

このプロンプトは共有利用を前提にしており、特定ドメインに依存しない汎用チェックを行います。

対象:
{{input}}

# 必須観点

1. 不明確・曖昧な表現がないか。
2. 抜け漏れ（要件不足）がないか。
3. 矛盾（前後の不一致）がないか。
4. テスト可能性（検証できる記述か）。
5. 再現性（手順が具体的で同じ結果を再現できるか）。
6. 数値・条件の明確性（閾値、対象範囲、前提条件）。
7. 例外・異常系の記載有無。
8. 用語の統一性。
9. 実装依存になっていないか（要件と実装手段の混同）。
10. 運用・保守観点の不足（監視、障害対応、更新運用など）。

# 出力形式

## 1. 総合評価

- 評価: S / A / B / C
- 判定基準:
  - S: 期待を大きく上回る品質で、模範例として推奨できる
  - A: 主要要件を満たしており、そのまま利用可能（軽微な改善余地は許容）
  - B: 利用可能だが、品質向上のために補足・修正を推奨
  - C: 重要な不足や不整合があり、修正後に再確認が必要
- 要約: 文書の品質を2文で総括。
- 判定理由: 主要な判断根拠を3点以内で列挙。

## 2. 指摘内容

- 各指摘に対し下記項目を出力する。指摘がない場合は「指摘なし」と明記する。
  - 重要度: 高 / 中 / 低
  - 概要: 指摘内容を1行で要約
  - 対象箇所: 見出し名 / 節番号 / 行番号など、特定できる単位。可能であれば該当行リンクも示す（例：[README.md#L10](/パス/README.md#L10)）。
  - 問題点: 問題を1文で記載
  - 根拠: なぜ問題かを簡潔に記載
  - 修正提案: 差し替え文案または追記案を具体的に示す
例：
```markdown
### ① 【高】異常系の記載が漏れている

- 対象箇所: 3.2 障害対応手順
- 問題点: 障害発生時の対応手順に異常系の記載がない
- 根拠:
異常系の記載がないと、障害発生時の対応が不明確になり、迅速な対応が困難になる
- 修正提案:
障害発生時の対応手順に、異常系の記載を追加する。
例：`障害発生時の初動対応、エスカレーションルール、復旧手順など。`
```

# ルール
- 目的、想定読者、前提条件など不明点があれば質問する（最大15回）
  - 質問は3つずつクイックピックを利用する
  - 優先度順に聞く
  - 回答を整理する
- 回答をもとに再度ドキュメントを分析する。
- 推測で断定しない。
- 指摘は具体的にし、可能なら修正文まで示す。
