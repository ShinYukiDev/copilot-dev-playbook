チーム全体で品質と速度を両立するための、実務特化の運用ガイドです。開発だけでなく、調査・保守・レビュー・ドキュメント更新までを対象にしています。

開発速度 品質担保 知識共有 保守性向上

1. まず押さえる原則

Copilotは「共同作業者」

  • 丸投げではなく、要件・制約・観点を渡すほど精度が上がる。
  • 正解を当てるより、候補を早く出して比較する用途が強い。
  • レビュー対象として扱い、必ず人が最終判断する。

成果を出す3条件

  • コンテキスト：仕様・設計・既存コードへのアクセス
  • 分解：タスクを小さくして順番に依頼
  • 検証：テスト・静的解析・観点レビュー

2. 開発フローに組み込む（図解）

以下のループを標準化すると、Copilot利用が属人化せずチーム資産になります。

3. プロンプト設計の型（そのまま使える）

実装依頼

Template A

目的: ○○機能を追加
制約: 既存API互換, N+1禁止
対象: △△Service, □□Repository
成果物: 実装 + テスト + 変更理由
観点: 可読性, 例外処理, 性能
バグ調査

Template B

症状: 〜で500エラー
再現条件: A手順で100%
仮説: Null参照 / 競合 / 設定漏れ
依頼: 原因候補を優先度順に列挙し
最小修正案を提案
コードレビュー

Template C

対象PR: #123
レビュー観点:
1) 破壊的変更の有無
2) 性能劣化リスク
3) 例外時のふるまい
4) テスト不足箇所
問い合わせ調査

Template D

問い合わせ内容: 〜
発生日時/頻度: 〜
影響範囲: ユーザー数, 業務影響
確認済み情報: ログ, メトリクス, 直近変更
依頼:
1) 原因候補を可能性順に3件
2) 追加で確認すべきデータ
3) 一次回答文（利用者向け）
4) 恒久対策の案

コツ: 「目的・制約・対象・観点」を固定フォーマット化すると、回答品質が安定します。

4. 開発タスク別ベストプラクティス

新規機能実装

  • いきなり実装させず、まず実装方針と影響範囲を出させる。
  • 生成コードには必ず「異常系テスト」を追加させる。
  • PR説明文の草案も同時生成し、レビュー時間を短縮する。

リファクタリング

  • 挙動維持を明記する（仕様変更なし）。
  • 関数分割、命名改善、重複排除を段階的に行う。
  • 差分が大きい場合は機械的変更と意味変更を分離する。

障害対応・保守

  • ログから時系列を要約させ、再現性の高い仮説から検証する。
  • 暫定対応と恒久対応を分けて提案させる。
  • 再発防止の監視・アラート追加まで依頼する。

テスト設計

  • 正常系だけでなく境界値・異常系を必ず列挙する。
  • ユニット / 結合 / E2Eの責務を明確に分ける。
  • 「落ちるべきテスト」を先に書く。

5. やってはいけない使い方

NGパターン

  • 要件なしで「全部作って」。
  • 生成コードを未検証でマージ。
  • セキュリティ要件や性能要件を省略。
  • 巨大な変更を一度に依頼。

推奨パターン

  • 小さな単位で依頼して即検証。
  • 設計意図を先に確認してから実装。
  • レビュー観点を固定化して品質を平準化。
  • 学びをdocs/プロンプトに還元。

6. チーム運用ルール（最小セット）

Step 1: 共通プロンプト整備

実装・調査・レビューのテンプレートを共有。

Step 2: PRチェック統一

性能・例外・セキュリティ・テストを必須観点化。

Step 3: ナレッジ蓄積

有効プロンプトと失敗例を残して再利用。

Step 4: 定例ふりかえり

速度と品質を指標化し、運用を毎月更新。

7. 即実践チェックリスト

開発開始前

  • 目的・完了条件を明文化したか
  • 制約（性能・互換・セキュリティ）を書いたか
  • 影響範囲の確認をCopilotに依頼したか

実装中

  • 小タスクで依頼しているか
  • 例外系・境界値を含めているか
  • 根拠の説明を求めているか

PR前

  • テスト結果を添付したか
  • 破壊的変更の有無を明記したか
  • 運用影響（監視・ログ）を確認したか

保守運用

  • 障害の再現手順を文書化したか
  • 再発防止策をチケット化したか
  • 有効だったプロンプトを蓄積したか

8. 30秒版まとめ

1) Copilotには「目的・制約・観点」を渡す
2) タスクは小さく分割して依頼する
3) 生成結果は必ずテストとレビューで検証する
4) 学びを設計書とプロンプトに戻してチーム資産化する

重要: Copilot導入の差は、個人スキルより「チーム運用設計」で決まります。
